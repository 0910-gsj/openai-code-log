### 📋 变更摘要
此次变更将 GitHub Actions 工作流的触发分支从通配符 `*`（所有分支）修改为特定分支 `master`。

### 🛑 代码评审意见

#### 1. 优点：资源优化与策略聚焦
*   **节省构建资源**：将触发范围从 `*` 收缩到 `master` 是一个积极的优化。
    *   **场景分析**：如果仓库中有大量开发分支（如 `feature-x`, `hotfix-y`），原本的 `*` 会消耗大量的 GitHub Actions 免费额度或付费积分来运行不必要的构建。
    *   **收益**：现在构建仅在合并到主分支时触发，确保了只有在代码进入生产环境前的最后关卡才进行严格测试，提高了构建效率。

#### 2. 缺点与风险：过时的命名规范
*   **分支命名过时**：`master` 分支在现代开源项目和 CI/CD 实践中已被**弃用**。
    *   **问题**：GitHub 官方现在默认推荐使用 `main` 作为主分支。如果项目未来迁移到 `main` 分支，此工作流文件将失效，导致构建无法触发。
    *   **建议**：应将 `master` 改为 `main`。

#### 3. 架构考量：硬编码带来的维护成本
*   **耦合度问题**：工作流配置中硬编码了 `master` 分支名。
    *   **风险**：如果团队决定调整分支策略（例如从 `master` 迁移到 `develop`，或者引入 `release` 分支），开发人员必须手动修改此 YAML 文件。这增加了维护成本，且容易因疏忽导致配置遗漏。

#### 4. 安全性与流程规范
*   **PR 触发逻辑**：将 `pull_request` 的触发目标也锁定为 `master` 是正确的。
    *   **逻辑**：这确保了只有针对 `master` 分支的 Pull Request 才会运行 CI 检查，防止对其他分支的合并请求绕过测试直接合并。

### 💡 改进建议

为了符合现代最佳实践并提升架构的健壮性，建议对代码进行如下调整：

**方案 A：使用现代分支名**
```yaml
on:
  push:
    branches:
      - main  # 使用 main 替代 master
  pull_request:
    branches:
      - main
```

**方案 B：支持多分支（灵活性更高）**
如果你的团队有 `develop` 分支也需要构建，建议使用数组：
```yaml
on:
  push:
    branches:
      - main
      - develop  # 包含开发环境构建
  pull_request:
    branches:
      - main
      - develop
```

**方案 C：基于路径过滤（性能最优）**
如果构建耗时较长，且只有特定目录（如 `src/`）的变更才需要触发完整构建，建议使用 `paths` 过滤器，而不是限制分支：
```yaml
on:
  push:
    branches:
      - main
    paths:
      - 'src/**'  # 只有 src 变更才触发
      - 'pom.xml' # 只有依赖变更才触发
  pull_request:
    branches:
      - main
```

**修改有效，但需优化。**
这是一个合理的 CI/CD 策略收紧，避免了无效构建。但鉴于 `master` 已是旧规范，建议**立即**将其改为 `main`，以确保代码库的现代化和可维护性。
